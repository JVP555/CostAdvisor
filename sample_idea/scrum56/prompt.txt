Estimate: 5 pts

A lot of companies buy the same product from more than one region — especially multinationals with plants in different countries — and that basically forces a different cost formula per region, because a big chunk of the cost is region-specific (labor being the obvious one). So region cant just be a label on a price, it has to be a real managed thing. It also gives us one clean place to standardize where we apply exchange rates, and its what makes cross-region comparisons actually possible.

Today: region is a String(20) in ≥5 places — IndexValue.region, IndexOverride.region, TeamIndexSource.region, CostModel.region, CostModel.destination_region.

Add:

A Region table (code, name, parent_id so subregion drops in later with no schema change). Seed the closed vocabulary: EU, NA, APAC, CN, IN, LA, MEA (+ Global used on feeds = 8th).

Migrate the string columns to FKs; backfill by mapping distinct existing strings → region rows.

Admin CRUD (UI lands in UI-7).

Note (merge call): the Intelligence schema hard-codes region as an enum in 5 tables — those become FKs to this entity.

Acceptance criteria:

Region is a row, not a string, everywhere above; existing data maps with no orphaned strings.

A subregion can be added as a child with no migration.
