"Link priced cost models to the library recipe instead of copying it (nesting that propagates)"

The nesting engine exists — services/formula_resolver.py expands component_type='formula' lines, scales weights multiplicatively, caps at MAX_CHAIN_DEPTH, detects cycles and guards the write path, with coverage in tests/test_weighted_formulas.py. This subtask is the half that never landed: getting it to reach a priced cost model.

What happens today

CostModelBuilder.jsx::loadTemplateIntoModel() calls GET /formulas/{id}/resolve and copies the flattened lines into FormulaComponent rows. The resolved line's depth, via_template_id, line_region and commodity_id are all dropped; weights are rounded (Math.round(effective_weight_pct * 10) / 10) and then renormalised over totalParts at save. FormulaVersion and FormulaComponent carry no reference to the template or combo the recipe came from.

Two failures follow, and both are quiet:

Editing a child template, or reloading a combo from the next catalog drop, changes nothing that is already priced.

On save the index link is re-established by name: cost_models.py::resolve_commodity_id() matches CommodityIndex.name exactly and takes the first row, returning None on a miss. _compute_indexed_cost() treats a component with no commodity_id as riding flat at ratio 1.0 and records no DataGap — so a mis-bound line looks like a healthy fixed line forever. Index naming moves under SCRUM-74's three-layer model, so this is due to get worse.

The decision inside this

A negotiated contract formula must not drift — those weights are what was signed. A should-cost estimate should track the library. The engine needs both and needs to be able to report which one a given version is; that choice is the interesting part of this subtask, not the plumbing.

Acceptance criteria

A cost model created from a library recipe records the template and the region/combo it resolved from, retrievable via the cost-model API.

Changing a child template's weights and re-evaluating a following version changes its should-cost; a pinned version's should-cost is unchanged, and the API states which mode the version is in.

Evaluating a priced cost model returns per-line depth and originating template, and those match GET /formulas/{id}/resolve for the same template + region.

A component whose index cannot be bound appears in an explicit gap list rather than silently riding flat; ShouldCostResult gains that surface (it has none today, unlike EvolutionResult).

Effective weights survive the round trip from combo to priced model without the current rounding drift, or the drift is reported.

Existing cost models with no template link keep evaluating exactly as they do now — regression covered by test.
