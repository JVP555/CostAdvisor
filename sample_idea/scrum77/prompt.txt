"INT-3 · Polymorphic dimension model + alias layer + query API"

Estimate: revisit — the story widened. Was 8 pts against the June drop.

Epic: W3-C · Taxonomy & Dimensions (docs/WAVE3_PLAN.md). Facts behind everything below: docs/DROP_2026-07_ANALYSIS.md §5.2. Concrete schema sketch to argue with: docs/CONTENT_MODEL.md.

What this is

Procurement questions cut sideways across the library — which of our products touch EUDR, what does this producer actually make, everything feeding this end market. Today that is a spreadsheet audit, because the model knows products and formulas but not the vocabulary a buyer slices by.

This story makes that vocabulary a first-class, queryable thing. The deliverable is the dimension layer and its query surface — schema, alias resolution, loaders, an API, and a report of what did not resolve. No faceted sidebar ships here; the sidebar in newDocsFolder/intelligence_mockup (19).html is the consumer, and it should be able to be built against this API without a schema change.

backend/app/models/region.py is the precedent worth copying: a vocabulary that used to be free text on several tables became managed rows, and nothing downstream had to be rewritten because the stable natural key (code) stayed the thing the app matches on.

Nothing of this exists yet — there is no dimension model, router or service under backend/app.

Shape

One polymorphic dimension_term + dimension_alias + one join, not a table pair per dimension. Sketch in docs/CONTENT_MODEL.md §"Dimensions".

Two reasons the four-table-pairs version gets expensive fast. First, the facets are not a closed set — the drop already implies functionality, industry / end market, compliance flag, application use, supply region and substitution risk, and Categories and Strategy will each want their own. Second, the cross-cutting query is a union over every shape you built, so each new facet costs a migration and an endpoint.

Three things the join needs that a plain tag table does not have:

subject_code NOT NULL, template_id nullable. Roughly a sixth of the payload's keys have no formula_templates row — orphan CURATED keys, route-only keys, GRP-* group pseudo-keys. A hard FK drops them at import and does not raise. Same rule as the editorial blocks.

Nullable region on the join. The assertions arrive keyed to formula, but the questions get asked per formula × region combo — which of my EU combos touch EUDR is the real question, and EUDR is an EU claim. FormulaTemplateComponent.region in backend/app/models/formula_template.py already carries exactly this semantic (NULL = applies to every region, set = region-specific, resolver prefers the specific row); reuse it rather than inventing a second convention.

Platform assertion vs team override. team_id NULL = our claim, set = the team's. Fork convention as chemical_families / formula_templates: origin_id back-link, uniqueness re-scoped with partial indexes (uq_chem_fam_platform_name / uq_chem_fam_team_name in alembic/versions/tx1a2b3c4d5e_taxonomy_spine_subfamily_forking.py).

The four "dimensions" are four different problems

This is the part the old ticket got wrong, and it is why SCRUM-141 splits. Only one of them is a loader.

Functionality — clean, and one trap. FUNCTIONALITY_TAXONOMY.json is a controlled vocabulary, FUNCTIONALITY_TAGS.json maps formulas onto it, and every tag value is in the taxonomy — no strays. Mechanical.
The trap: FAMILY_FUNCTIONALITY_DEFAULT.json and SUBFAMILY_FUNCTIONALITY_OVERRIDE.json also carry functionality labels, and their vocabulary has zero overlap with the taxonomy (Base Chemical/Feedstock, Surfactant/Emulsifier, … vs Adsorption, Advanced oxidation, …). They are two different naming schemes for the same idea. Loading both under one kind produces a facet with two disjoint halves and no way to tell which half a user is filtering on. Either they are two kinds, or one maps onto the other — that mapping is a judgement call and belongs in the decision file, not in loader code.

Industry / end market — the classifier survived, the file did not. INDUSTRY_RULES.json serialised every regex to {} ([[{}, "Adhesives & Sealants"], …]) and the extractor still reported ok. The rules are intact in newDocsFolder/intelligence_mockup (19).html:8698.
Recovering them is the easy half. Running them over the free-text industry strings in CURATED_CONTENT.json is where the work is: a real minority of distinct strings match no rule (Home care, Industrial, Cross-sector, Process industries, Oleochemical feedstock, Composites…), and another slice matches more than one, where first-match-wins in source order silently picks. There are also plain casing/whitespace collisions on top. So the classifier's output is a draft mapping that needs review before it becomes a facet, and it has to be materialised as alias rows rather than re-run at query time — otherwise reordering the rule list quietly reclassifies the library.

Compliance flags — two sources, no adjudicator. Items are {flag, type, desc, name} dicts in both CURATED_CONTENT.json and SUPPLY_DEMAND_COMPLIANCE.json, except a set of bare strings in CURATED with no flag and no type at all. The two files overlap on most formula keys, and about a third of those shared keys assert different sets of flags.
Worth knowing before you plan the merge: where both files name the same flag they agree on severity — the disagreement is membership, one file naming a regulation the other omits. So a union is not automatically the safe default; it means shipping every claim either source made, on a compliance facet, to a customer. Which source wins (or whether it is per-claim) is a domain call — docs/CONTENT_MODEL.md §"Two data decisions that must precede the loader" flags it as needing an answer before the loader is written. Today the mockup "decides" by JS duplicate-key shadowing, which is not a decision.

Producers — not a dimension, and not Supplier. backend/app/models/supplier.py has team_id NOT NULL under the strict-tenant policy in alembic/versions/h8i9j0k1l2m3_enable_rls.py. There is no row shape there for BASF-as-a-company-that-exists; a supplier only exists inside a team that buys from it. So this is a new platform entity with a join, and it needs three things a tag table does not:

share: 0 means not disclosed, not zero — nearly every supplier row carries it, and many notes say so explicitly. Store the flag alongside the number or the UI ships "BASF — 0% market share".

Alias resolution is not a function. canonicalizeSupplierName() at newDocsFolder/intelligence_mockup (19).html:8791 splits ' / ' strings into separate entities, so one raw string can produce N producers.

SUPPLIER_ALIASES.json is a partial map, not a complete one. It covers a minority of the distinct raw supplier names in CURATED_CONTENT.json — treating it as the canonicalisation step leaves most names unresolved and silently duplicated.

This story owns the producer entity and the alias layer. That is settled, and it is written the same way in the tickets that touch it: docs/WAVE3_PLAN.md W3-D SUP-1/SUP-2 describe the same platform company master and consume this one rather than building a second; SCRUM-74 / DB-7 stores the index-specific producer role and references the entity by FK, holding no company records of its own; SCRUM-32's alias-canonicalisation dependency points here. Coordinate with W3-D SUP-1/SUP-2 on the shape before you freeze the schema — two masters is the failure mode.

One more note on kinds

FUTURE_OUTLOOK.json's substitution entries have near-unique free-text titles and a risk level that is nominally Low/Medium/High but carries out-of-vocabulary values in the payload. A term table over the titles yields one term per row, which is not a facet. The bounded, queryable part is the level. Worth deciding which kinds actually earn a term table and which are a severity on a block, rather than creating a kind for each heading in the source.

Tenancy

Use the platform-readable + team fork policy, the one in alembic/versions/rls1f2a3b4c5d_fix_rls_formula_and_custom_fx.py:

USING (<bypass> OR team_id IS NULL OR <member_of>)

Not the strict-tenant USING (<bypass> OR <member_of>) shape from h8i9j0k1l2m3. Under strict tenant every platform term is invisible to every team, so the facet is empty for everyone on day one and the bug looks like a loader failure.

The team-scoped end of the query still scopes itself: RLS on products already narrows "which of my products touch EUDR" without the endpoint filtering by team at all.

Reads and writes are separate gates. Platform writes go through app/services/permissions.py::has_platform_permission + UserPlatformRole; the dimensions.* keys they check come from SCRUM-76's single permission migration, one alembic revision carrying content.* and dimensions.* together. This story consumes those keys and does not add a second migration.

Query API

The same join has to answer at two grains, and this is where the old ticket's single "products" framing breaks:

Team grain — which of my products / combos carry this term. Backs Portfolio and the audit use case.

Platform grain — which formulas carry it. Backs the Intelligence library, which renders platform tiles, not a team's products. (Same grain error called out on SCRUM-134 in docs/JIRA_TRIAGE_2026-07.md.)

Faceted over (kind, code) rather than an endpoint per question — "everything exposed to EUDR" is an example of the query, not the name of it. And the response should carry enough to audit the hit: which alias matched the raw value, whether the assertion is platform or a team override, and the region it applies to. A bare list of product names cannot be checked by the person who has to act on it.

One read-path note carried over from docs/CONTENT_MODEL.md: an ID card wants dimensions alongside the payload's editorial block types in one round trip. The card is two calls by design. The composed editorial + dimensions read is GET /formulas/{code}/intelligence, owned by SCRUM-76 / CON-7 — dimensions go inside it. The derived payload at formula × region combo grain is the other call, owned by SCRUM-75 / SCRUM-134. This story ships neither endpoint; it ships the dimension half that CON-7 composes.

Done

Terms, aliases and assertions load from the drop's reference data, idempotently, and re-running changes nothing.

The analyst-decided parts (industry mapping, flag adjudication, producer canonicalisation) live in a checked-in, reviewable decision file — the pattern newDocsFolder/pipeline/sync_decisions.py already uses for the seed grids — and re-importing that file is what changes the DB. Not in loader branches.

Every raw value that did not resolve is listed by a report, not swallowed. That report is the analyst's work queue and it is how anyone checks the load actually worked.

GET a term list per kind, and a faceted query at both grains, with the alias/region/scope provenance on each hit.
