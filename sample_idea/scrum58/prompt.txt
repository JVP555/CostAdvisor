Est. 13 pts — this one's genuinely big (four related pieces). Happy to split it into separate stories if that's easier to run.

A should-cost is basically a recipe — this product is 60% one index, 10% another, plus a margin — and the number stays live because those index prices move. For that to actually compute, the app has to hold the recipe as real weighted parts, not as a line of text it cant do math on, which is roughly where our shipped catalog is today. This is what makes the recipes real and computable, picks the right one for a buyers region, and lets one recipe feed into another — which is how chemicals genuinely work, since an intermediate like a solvent blend is both a product we price and an ingredient in the products built on top of it.

Where we are today: weighted components already exist, but only at the instance level — FormulaComponent (label, commodity_id, weight) hangs off FormulaVersion (which already has formula_type, margin_type/value, incoterm). Incoterm is already stored in the right places (CostModel / FormulaVersion / ActualPrice / CommodityIndex), so that part's settled. The gap: the platform FormulaTemplate is expression-string-only, so the 676 seed combos have nowhere to live as real components.

What we're adding:

A component child on FormulaTemplate that mirrors FormulaComponent, with a component_type of direct / proxy / fixed and a nullable commodity_id — the 874 "fixed"/margin lines don't point at an index. Heads up: "fixed" there is a sentinel value, not a real index, so it shouldn't turn into an index row called "fixed".

A resolver keyed by formula × region (it's formula × region, not family × region × form — the form is constant per formula). It auto-loads the template when a product is created, with the fallback decided below.

A per-(formula × region) coverage table, because coverage_tier and data_confidence actually vary by region for 67 of the 257 formulas, so they can't sit on the region-agnostic template.

Support for a formula feeding another formula (the "lego" stacking — e.g. SOL-ACE-LIQ is both a formula and an index other formulas reference).

Decisions (locked):

Resolver fallback — try the exact formula × region first; if it's missing, fall back to the Global template; if there's no Global one either, fall back to EU; only flag if none of those exist.

Lego depth — products stack in tiers (a tier-2 product uses tier-1 products as inputs, tier-3 uses tier-2, and so on), so chaining runs as deep as the tiers go — not capped at one level. The tiers only build upward, so it shouldn't loop by design; we'll keep a cheap depth cap as a seatbelt against a bad entry, and skip any elaborate cycle-resolution.

Done when:

A weighted platform formula stores as components, not a stringified expression.

Creating a product auto-loads the template by formula × region (falling back Global → EU as above), and should-cost computes from the components.

The existing advanced expression path still works — no regression.

Sub-tasks:

FormulaTemplate component child (+ component_type, nullable commodity_id)

Per-(formula × region) coverage table

Resolver (formula × region) + fallback (Global → EU)

Formula-as-input chaining support (tiered, with a depth cap)
