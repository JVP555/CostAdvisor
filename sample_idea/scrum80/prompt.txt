"FD-1 · Proxy derivation engine & swap backlog"


What changed

The old body says the problem is paywalls: most of the indexes our formulas rely on can't be pulled directly because they're licensed, so we approximate them from free public data, and exactly two feeds have no free stand-in and get marked no-live-source.

Both halves of that trace to code rather than to data. The "two blocked feeds" is _NEW_BLOCKED_CODES = {"ILM-MB", "RUT-MB"}, a hardcoded set at backend/seed_index_metadata.py:152. And the drop's index access column (Free / Proxy / Subscription in newDocsFolder/seed/tables/index_feeds.csv) measures effective access after proxying, not native licensing — it is not evidence the paywalls went away, and it is not evidence the old premise holds either. SCRUM-26's premise stands.

The blocker that actually stops a cost line from being priced is missing numbers. In newDocsFolder/seed/tables/type_codes.csv a type-code carries a resolution state; the codes marked no_series all name a resolves_to commodity that genuinely exists in index_commodities.csv — with has_series = False. The join succeeds and the numbers are absent. The type-codes that resolve to no series carry real cost weight, not two feeds. A client's Fastmarkets key does not fix it; sourcing the series does, and that is Phase 0 procurement in docs/WAVE3_PLAN.md, not this ticket.

So FD-1's job widens: it is not only "execute the approximation", it is "follow the type-code's resolution, execute a derivation where one is configured, and say plainly when neither is possible."

Grain

The proxy relationship lives at type-code grain. A cost line names a type-code (combo_lines.type_code); the type-code resolves to a price series (type_codes.resolves_to → index_commodities.commodity_key).

CommodityIndex is neither end of that today: seed_index_metadata._new_base_and_region() (line 71) splits PHOS-WB into commodity PHOS plus region WB, and after DB-5 lands (SCRUM-74) CommodityIndex becomes the price series. Anything written per-index cannot express that one series backs many type-codes — and roughly a quarter of all indexed cost weight reaches brent through dozens of separate codes. SCRUM-74 makes that aggregation queryable; this engine has to be written at the grain it aggregates over, or the two never meet.

What this story owns

Derivation — where a spec is configured, run it and produce a value series that is tagged as derived and names what it came from.

Swap semantics — swap_priority and ideal_index persisted with their meaning intact, and the sourcing backlog ranked by the weight sitting behind each code.

Unresolvable on the value path — a request for a number that cannot exist comes back as a reported state with a reason, not a null and not a carried-forward value.

Consumes, does not build. The type-code / card / series tables are DB-5, and the plain reads over them — the resolution chain for a type-code, and indexed cost weight aggregated by resolved series — are SCRUM-74's Resolution + concentration query API. This story calls that endpoint. It does not re-implement the chain and does not ship a second concentration query. What it owns on those columns is their meaning: the A/B/C rank and ideal_index surviving the loader, and what the engine does with each resolution state.

Swap priority is a sourcing backlog rank, not a confidence score

newDocsFolder/PROXY_SWAP_REGISTRY.md defines the three ranks, and they are not an accuracy ladder:

A — genuinely swappable. A better index exists, and it's named in ideal_index. Buying or sourcing it improves the number overnight.

B — upstream feedstock or energy stand-in. Defensible by design; a direct index would be better but this is not broken.

C — permanent by design. Electricity tracks electricity, HDPE packaging tracks crude. The proxy already is the right index.

seed_index_metadata._new_retrieval() (line 155) currently folds A into good_proxy and everything else into weak_proxy. That reads a C-ranked code — one that is already correct — as a rough approximation, and it drops the rank entirely. SCRUM-74 hands that fix over to this story explicitly.

ideal_index is prose naming a series we do not have: none of its values correspond to any commodity_key in the drop. It cannot be an FK today. It becomes one the day the series is sourced, and the swap backlog is precisely the list of days worth paying for.

Gotchas

proxy_status is stated twice and disagrees. Both combo_lines and type_codes carry it, and they contradict each other on a meaningful minority of indexed lines — in both directions (direct vs proxy), plus unclassified against both. resolution agrees on every line, so the disagreement is confined to proxy_status. Whichever column is read, the other says something else. SCRUM-74's validation run surfaces this as a finding; which column is authoritative still needs deciding before anything branches on it.

resolution has three states. resolved, no_series, and ambiguous — the ambiguous ones carry a blank resolves_to, so they are neither resolved nor cleanly blocked. Binary handling files them somewhere wrong.

The current resolver cannot tell you why a number is what it is. get_single_index_value() (backend/app/services/data_resolver.py:302) falls back region → GLOBAL → any region → most recent earlier period. That carry-forward is deliberate for costing (it stops ratios flattening to 1.0), and it means the caller cannot distinguish current from stale from never-had-it. FD-1's output has to carry that distinction even though the costing path keeps the fallback.

Margin sits inside the 100% weight total now. Every combo with lines sums to exactly 100 and margin is one of those lines. It is not indexed and must not enter any weight-share aggregation this engine computes.

The arithmetic already exists. compute_composite_value() (data_resolver.py:266) evaluates a stored spec over other indexes through safe_eval_expr, with a recursion cycle guard and a "missing component → None, never fabricate a 0" rule. PROXY_OPERATIONS in app/constants/index_metadata.py:26 overlaps that arithmetic almost completely. What is genuinely absent is any execution call site for proxy_logic at all — it is written by the seed loader, edited through PUT /api/indexes/{id}/proxy-logic (routers/indexes.py:112) and DerivedIndexesModal.jsx, and read by nothing. That gap, not a second evaluator, is the work.

Done

Infrastructure, not a surface. There is no Index drawer or proxy admin page in scope here — proxy management already lives in the Index Library (e33597e) and stays there. Done means the derivation runs and is queryable from the API, the derived numbers carry their provenance, the swap backlog is ranked, and the unpriceable set is enumerable instead of just absent.

The resolution-chain read and the cost-weight-by-series concentration query are SCRUM-74's (Resolution + concentration query API). This story calls them; they are not restated here as its own criteria.

The swap backlog is queryable ranked by the cost weight sitting behind each type-code, so an A-ranked code carrying a lot of weight sorts above an A-ranked code carrying little.

A value produced from a configured derivation is retrievable, is tagged as derived, and names the base series and operation behind it. It is not indistinguishable from an observed value at any point a consumer sees it.

Asking this engine for a value on a type-code whose resolution is no_series returns an explicit unresolvable state naming the series it wanted, rather than a null or a carried-forward value.

Loading the drop preserves A/B/C and ideal_index as distinct values, not folded into retrieval_status.

Tests assert on resolution state, not on a membership list of specific codes.

Not in scope

Sourcing the missing series (procurement — docs/WAVE3_PLAN.md Phase 0). The type-code / card / series tables themselves and the plain resolution and concentration reads over them (DB-5 and Resolution + concentration query API, both SCRUM-74). The Index Library UI.
