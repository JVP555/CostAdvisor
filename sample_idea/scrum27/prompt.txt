"Sheet round-trip service (export slice -> author offline -> re-import -> diff -> apply)"

The pipes that move data in and out of the platform, built once as a mechanism with several payloads rather than once per surface.

The pattern already exists and is worth reusing rather than reinventing. newDocsFolder/pipeline/sync_decisions.py reads exactly two named sheets back out of a returned workbook, matches rows by position against a known column order, writes them to decisions/*.csv, and explicitly ignores everything else because the data sheets are regenerated. That last part is the load-bearing design choice: the round-trip declares which columns a human owns, and refuses to silently absorb edits to the ones it will overwrite.

Three payloads want the same mechanism: the seed decision grids, editorial content (docs/WAVE3_PLAN.md W3-I, no epic on the board yet), and Strategy levers (W3-H). Building three separate exporters is how they drift.

Things the mechanism has to handle that a single-payload version would not:

A filtered slice, not the whole table. An intelligence officer exports the unreviewed blocks for one subfamily, not the library.

A diff before apply. The re-import produces a reviewable changeset — what would change, from what to what — and applying it is a separate action.

Round-trip identity. A returned sheet has to re-key to the rows it came from after someone has sorted it, hidden columns, or pasted values. sync_decisions.rows_of() handles the header-offset case by scanning for the header row; the key-stability case is the one to think about.

Concurrent edits. Two officers exporting overlapping slices is normal, not an edge case.

The presentation-side scope that used to sit on this ticket — client-ready formatted exports and scheduled delivery packs — is not infrastructure and is not Wave 3. The structured-export / BI / ERP scope that used to sit on SCRUM-35 is folded here as a shape constraint only: the export format should be machine-readable enough that a BI consumer is a later adapter, not a rewrite. Neither is in scope now; they are recorded so they are not silently re-added.

Done when

An export produces a sheet for a caller-specified filtered slice, with the human-owned columns and the read-only columns distinguishable in the file itself.

Re-importing an unmodified export produces an empty changeset.

Re-importing an edited export produces a changeset naming each affected row, column, old value and new value, and applying it is a distinct call.

A returned sheet whose rows have been reordered still re-keys correctly.

A returned sheet with edits in a regenerated column is rejected or reported, never silently absorbed.

Import runs are persisted and inspectable after the fact.
